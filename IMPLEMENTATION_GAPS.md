# CareOS implementation gap ledger

**Audit date:** 13 September 2026; implementation evidence updated 15 September 2026  
**Overall status:** **foundation and clickable prototype; not production-ready**

This ledger reconciles the repository with the authoritative 46-page _CareOS Complete Build Specification_, the repository architecture/roadmap documents, and the checked-in implementation. It is intentionally evidence-based: a clickable route, a database table, or a dependency is not counted as a completed production capability unless the behavior is persisted, authorized, tenant-safe, audited, and covered by the required tests.

## Audit scope and interpretation

Reviewed:

- all maintained backend, frontend, migration, Compose, CI, script, test, and Markdown files;
- the full 46-page build specification PDF;
- the generated frontend lockfile through a clean `npm ci` installation;
- currently available quality gates.

The current source correctly describes itself as a **runnable engineering foundation**. The 79 routes are useful prototype coverage, but they are not completed Module 1, Module 2, or clinical workflows.

## What is already usable

- Java/Spring Boot, React/TypeScript, PostgreSQL, Redis, MinIO, Mailpit, Docker Compose, Flyway, and GitHub Actions scaffolding exist.
- The frontend has a responsive visual shell, authenticated session gate, server-derived expiry lock and event-driven resume revalidation without polling, public password recovery, recent-authenticated MFA enrollment/recovery-code self-service, a server-backed organization switcher, accessible error/loading/denied states, screen navigation/search, keyboard focus styling, and all 79 registered route states.
- The backend independently exposes the 79-screen registry at `/api/public/prototype-screens`.
- A database foundation exists for users, credentials, password reset, MFA/recovery, invitations, sessions, organizations, memberships, facilities, authorization/event catalogs, append-only audit events, immutable outbox events, actor-scoped idempotency records, encrypted tenant notification requests, and append-only quarantine/scan evidence.
- All 15 current operations have a checked OpenAPI 3.1 contract, validated correlation IDs, and RFC 9457 validation/security error responses. Shared tenant-route, cursor/filter, concurrency, idempotency, retry, and session-lifecycle conventions plus checked generated frontend types/client are in place for future operations.
- Browser identity uses persisted credentials and Redis sessions with CSRF/origin enforcement, throttling, password recovery, encrypted TOTP, one-use recovery codes, recent authentication, and revocation. The browser now exposes those policy-neutral self-service flows while keeping reset/enrollment/recovery material memory-only and runtime-validated.
- Disposable PostgreSQL 18 tests verify Flyway migrations, restricted runtime credentials, actor-only membership discovery, transaction-bound membership/permission authorization, cross-tenant RLS denial, atomic governance evidence, concurrent request replay, outbox delivery transitions, encrypted notification lifecycle transitions, and immutable tenant-bound document-security evidence.
- Nine document/notification/job/worker/scheduler capabilities have typed ports, validated metadata, exact status registration, and default adapters proven to fail before I/O. Private quarantine, malware scanning, durable Redis job transport, and encrypted PostgreSQL notification persistence/leasing have opt-in adapters with isolated integration coverage; all remain disabled by default and the other five have only unavailable adapters. The mandatory PostgreSQL foundation now separately persists quarantine metadata and scanner attestations without marking any external capability available.
- Frontend API generation drift, strict indexed-access type checking, linting, formatting, unit tests, production build, dependency audit, and installation currently pass. See [verification snapshot](#verification-snapshot) for limits.
- CI dependencies are full-SHA pinned and least-privilege bounded; dependency review, CodeQL, Trivy source/image checks, CycloneDX image SBOMs, Dependabot coverage, digest-pinned containers, and non-root runtime contracts are checked into the repository. Hosted enforcement still requires a real target-repository run.
- The backend emits ECS JSON with correlation/trace context, exposes public status-only `/livez` and PostgreSQL/Redis-aware `/readyz`, and provides authenticated Prometheus metrics. OTLP export is disabled by default; `docs/OPERATIONS.md` records the signal contract and production acceptance checklist.
- Spring Security and Nginx now enforce explicit response-header policies, the frontend CSP is strict and same-origin, the Nginx API proxy is bounded, and a production-only startup guard rejects local profiles/material and insecure database, Redis, SMTP, cookie, browser-origin, S3, or enabled-OTLP settings. `docs/PRODUCTION_SECURITY.md` records the deployment acceptance boundary.

These are valuable starting points. None are a substitute for the production behavior below.

## Recommended implementation sequence

1. **Close Phase 0:** resolve all Priority 0 architecture, authentication, tenancy/RLS, contracts, persistence, audit/outbox, test, and CI gaps. Capture an evidence-based Phase 0 PASS only after backend and browser gates pass.
2. **Freeze approved M1 inputs, then deliver M1 vertical slices:** start with tenant-safe organization and access foundations, then network/services/configuration, and finish with activation/history/audit/export.
3. **Freeze approved M2 inputs, then deliver M2:** reuse M1 identity/RBAC/configuration instead of creating parallel models.
4. **Proceed M3 through M13 strictly in specification dependency order.** Each module needs a gap ledger, traceability matrix, approved policy/mockups, real persistence, tests, and owner acceptance before the next module begins.
5. **Treat clinical/COS and AI work as safety-sensitive:** do not use the placeholder UI as a visual or workflow freeze.

## Definition of complete for any item above

Mark an item complete only when its approved route/screen, permission, handler/service, database migration, state transition, validation, audit/outbox record, security controls, responsive/accessibility states, and automated tests all exist and pass. Client-only behavior, an unreachable endpoint, a schema without an enforced workflow, or a skipped critical test is **not** completion.
