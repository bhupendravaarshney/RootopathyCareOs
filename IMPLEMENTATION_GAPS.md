# CareOS implementation gap ledger

**Audit date:** 13 September 2026  
**Overall status:** **foundation and clickable prototype; not production-ready**

This ledger reconciles the repository with the authoritative 46-page _CareOS Complete Build Specification_, the repository architecture/roadmap documents, and the checked-in implementation. It is intentionally evidence-based: a clickable route, a database table, or a dependency is not counted as a completed production capability unless the behavior is persisted, authorized, tenant-safe, audited, and covered by the required tests.

## Audit scope and interpretation

Reviewed:

- all maintained backend, frontend, migration, Compose, CI, script, test, and Markdown files;
- the full 46-page build specification PDF;
- the generated frontend lockfile through a clean `npm ci` installation;
- currently available quality gates.

The current source correctly describes itself as a **runnable engineering foundation**. The 79 routes are useful prototype coverage, but they are not completed Module 1, Module 2, or clinical workflows.

## What is already usable

- Java/Spring Boot, React/TypeScript, PostgreSQL, Redis, MinIO, Mailpit, Docker Compose, Flyway, and GitHub Actions scaffolding exist.
- The frontend has a responsive visual shell, screen navigation/search, basic keyboard focus styling, and all 79 registered prototype routes.
- The backend independently exposes the 79-screen registry at `/api/public/prototype-screens`.
- A database foundation exists for users, credentials, password reset, MFA/recovery, invitations, sessions, organizations, memberships, facilities, authorization/event catalogs, append-only audit events, immutable outbox events, actor-scoped idempotency records, and encrypted tenant notification requests.
- All 15 current operations have a checked OpenAPI 3.1 contract, validated correlation IDs, and RFC 9457 validation/security error responses.
- Browser identity uses persisted credentials and Redis sessions with CSRF/origin enforcement, throttling, password recovery, encrypted TOTP, one-use recovery codes, recent authentication, and revocation.
- Disposable PostgreSQL 18 tests verify Flyway migrations, restricted runtime credentials, actor-only membership discovery, transaction-bound membership/permission authorization, cross-tenant RLS denial, atomic governance evidence, concurrent request replay, outbox delivery transitions, and encrypted notification lifecycle transitions.
- Nine document/notification/job/worker/scheduler capabilities have typed ports, validated metadata, exact status registration, and default adapters proven to fail before I/O. Private quarantine, malware scanning, durable Redis job transport, and encrypted PostgreSQL notification persistence/leasing have opt-in adapters with isolated integration coverage; all remain disabled by default and the other five have only unavailable adapters.
- Frontend type checking, linting, formatting, unit tests, production build, and dependency installation currently pass. See [verification snapshot](#verification-snapshot) for limits.

These are valuable starting points. None are a substitute for the production behavior below.

## Data model and database gaps

The current migrations are deliberately labelled a foundation. They must be extended by controlled, additive migrations as modules are implemented.

- Add the standard columns and constraints required by the specification: UUIDv7 strategy, actor columns, non-null tenant IDs for tenant-owned records, revisions, effective-date ranges, status constraints, reasons, supersession lineage, composite foreign keys, and appropriate indexes.
- Retain the implemented append-only general audit/outbox evidence controls and add database enforcement for maker-checker separation, final active owner/administrator protections, prohibited effective-date overlaps, and no destructive cascade into historical records.
- Define tenant-safe seed strategy. Current synthetic organization/facility rows are useful local data, but runtime production data must not be created by an unconditional foundation migration.
- Extend the PostgreSQL 18 migration/RLS suite with every new table, constraint, role, and policy; the current suite covers the 20-table foundation through `V7`, including actor discovery, fail-closed authorization, invitation/notification RLS, append-only authentication/general audit evidence, concurrent idempotency, outbox delivery, and encrypted notification transitions.
- Add lifecycle schemas and state transition controls before exposing each workflow. Tables alone do not satisfy the state-machine, reason, approval, audit, and outbox rules.

## Frontend and prototype-to-product gaps
