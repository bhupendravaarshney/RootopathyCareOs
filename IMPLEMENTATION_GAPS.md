# CareOS implementation gap ledger

**Audit date:** 13 September 2026; implementation evidence updated 15 September 2026  
**Overall status:** **Phase 0 repository reference checkpoint complete; production acceptance pending; business modules remain prototype-only**

This ledger reconciles the repository with the authoritative 46-page _CareOS Complete Build Specification_, the repository architecture/roadmap documents, and the checked-in implementation. It is intentionally evidence-based: a clickable route, a database table, or a dependency is not counted as a completed production capability unless the behavior is persisted, authorized, tenant-safe, audited, and covered by the required tests.

## Audit scope and interpretation

Reviewed:

- all maintained backend, frontend, migration, Compose, CI, script, test, and Markdown files;
- the full 46-page build specification PDF;
- the generated frontend lockfile through a clean `npm ci` installation;

The current source correctly describes itself as a **runnable engineering foundation**. Its safely implementable Phase 0 mechanics are complete behind a provisional, disabled-in-production reference policy. The 79 routes are useful prototype coverage, but they are not completed Module 1, Module 2, or clinical workflows.

## What is already usable

- Java/Spring Boot, React/TypeScript, PostgreSQL, Redis, MinIO, Mailpit, Docker Compose, Flyway, and GitHub Actions scaffolding exist.
- The frontend has a responsive visual shell, authenticated session gate, server-derived expiry lock and event-driven resume revalidation without polling, public password recovery, recent-authenticated MFA enrollment/recovery-code self-service, a server-backed organization switcher, accessible error/loading/denied states, screen navigation/search, keyboard focus styling, and all 79 registered route states.
- The backend independently exposes the 79-screen registry at `/api/public/prototype-screens`.
- A 35-table database foundation exists for browser and service identity, organizations/memberships, authorization and operation/event policy, invitation/token lifecycle, maker-checker approval, governance delivery/deduplication, encrypted notification state, and append-only document evidence.
- New application-generated identifiers use a shared RFC 9562 UUIDv7 generator with process-local monotonic ordering; Flyway V13 establishes 12 native defaults and V16/V17 add three more without rewriting or rejecting historical identifiers.
- All 21 current operations have a checked OpenAPI 3.1 contract, validated correlation IDs, and RFC 9457 validation/security error responses. Shared tenant-route, cursor/filter, concurrency, idempotency, retry, and session-lifecycle conventions plus checked generated frontend types/client are in place for future operations.
- Browser identity uses persisted credentials and Redis sessions with CSRF/origin enforcement, throttling, password recovery, encrypted TOTP, one-use recovery codes, recent authentication, revocation, governed invitations/account linkage, and database-backed maker-checker administrative MFA reset. Reset, invitation, enrollment, and recovery material remain one-use or memory-only as appropriate.
- The separate service-identity boundary authorizes an exact credential digest, tenant, purpose, non-interactive role, and operation without accepting a human session or membership; provisioning, rotation, and worker activation remain production-owned work.
- Disposable PostgreSQL 18 tests verify Flyway migrations, restricted runtime credentials, actor-only membership discovery, transaction-bound membership/permission authorization, cross-tenant RLS denial, atomic governance evidence, concurrent request replay and consumer delivery, outbox delivery transitions, encrypted notification lifecycle transitions, immutable tenant-bound quarantine/scan/promotion/access-grant/retention evidence, and append-only consumer receipts.
- Nine document/notification/job/worker/scheduler capabilities have typed ports, validated metadata, exact status registration, and default adapters proven to fail before I/O. Private quarantine, malware scanning, clean-document promotion, signed document access, immutable document retention/legal-hold application, durable Redis job transport, and encrypted PostgreSQL notification persistence/leasing have disabled-by-default opt-in adapters with isolated integration coverage; worker execution and scheduler execution retain unavailable adapters. The mandatory PostgreSQL evidence store persists quarantine metadata, scanner attestations, clean-promotion proof, URL-free signed-access grant evidence, and provider-version-hashed retention proof without exposing a public workflow.
- Frontend API generation drift, strict indexed-access type checking, linting, formatting, unit tests, production build, dependency audit, and installation currently pass. See [verification snapshot](#verification-snapshot) for limits.
- CI dependencies are full-SHA pinned and least-privilege bounded; dependency review, CodeQL, Trivy source/image checks, CycloneDX image SBOMs, Dependabot coverage, digest-pinned containers, and non-root runtime contracts are checked into the repository. Hosted enforcement still requires a real target-repository run.
- The backend emits ECS JSON with correlation/trace context, exposes public status-only `/livez` and PostgreSQL/Redis-aware `/readyz`, and provides authenticated Prometheus metrics. OTLP export is disabled by default; `docs/OPERATIONS.md` records the signal contract and production acceptance checklist.
- Spring Security and Nginx now enforce explicit response-header policies, the frontend CSP is strict and same-origin, the Nginx API proxy is bounded, and a production-only startup guard rejects local profiles/material and insecure database, Redis, SMTP, cookie, browser-origin, S3, or enabled-OTLP settings. `docs/PRODUCTION_SECURITY.md` records the deployment acceptance boundary.

These are valuable starting points. None are a substitute for the production behavior below.
