# CareOS architecture

## Decision

CareOS begins as a modular monolith. Java/Spring Boot owns domain logic, authorization, transactions, data access, jobs and external integration ports. React/TypeScript owns accessible browser experiences. Node.js is used to build and test the frontend; it is not a second business backend.

## Dependency rule

Domain code must not depend on HTTP, database or vendor implementations. Application services coordinate use cases. Infrastructure implements ports. Web/API controllers translate transport contracts. Cross-module changes occur through explicit interfaces and outbox events.

Eleven ArchUnit tests currently enforce framework-free domain packages, inward application dependencies, infrastructure/API separation, API controller placement, cycle-free top-level modules, exclusion of the scanner-only quarantine stream from API packages, exclusion of job/notification claim-completion mechanics from API packages, prevention of API-level bypass around durable document-security, promotion, signed-access, retention, or transactional consumer-inbox orchestration, and use of the shared UUIDv7 generation strategy instead of direct production UUIDv4 calls. Every production module must retain the `domain`, `application`, `infrastructure`, and `api` direction established by the prototype, identity, tenancy, governance, and platform-capability foundations.

The frontend root composes pages and features. Pages may compose features and shared UI; a feature may depend inward on the checked API, data, and shared components; shared layers may not import a feature; and one feature may not reach directly into another. `npm run architecture:check` parses TypeScript imports and enforces this direction in CI, with negative fixtures for reverse, cross-feature, API-to-page, and source-escape dependencies. The fourteen bounded features are `session`, `administration`, `workforce`, `patient`, `scheduling`, `encounter`, `assessment`, `document`, `ai`, `careplan`, `followup`, `billing`, `reporting` and `integration`; later business features must follow the same boundary and be composed at a page or root entry point. After session and organization gates, the root admits only IDs in the checked screen registry. Unknown hashes render a non-reflective page with no active screen and no business component; registry lookup cannot silently substitute a default screen. Named Playwright projects exercise the reference UI at exact 1440/1024/768/390/320 widths; each registered route fails on serious Axe findings or body/document overflow, while navigation checks enforce the persistent-shell and drawer boundary.

## Tenancy and security

Every tenant-owned row carries `organization_id`. The runtime uses a restricted `careos_app` database role while Flyway uses a separate migration owner. Actor-only, read-only transactions expose only the authenticated actor's live memberships and selectable organizations. `TenantAuthorizationOperations` starts a fresh tenant transaction, binds organization, actor, purpose, and correlation settings, locks and revalidates a live membership, checks a migration-owned permission mapping, and only then supplies an `AuthorizedTenantContext` to work executed in that same transaction. Forced RLS remains defense in depth.

New application-created identifiers come from the shared RFC 9562 `UuidV7Generator`, which uses secure random state and provides process-local monotonic ordering across equal milliseconds or a local clock rollback. Flyway V13 requires PostgreSQL 18 and assigns native `uuidv7()` defaults to the original 12 database-generated identifier columns; V16, V17, and V22 add four more, V23 adds the owner-transfer request default, V26 adds organization identifiers, and V27 adds organization addresses and contacts. Existing and explicitly supplied UUIDs remain valid. The timestamp and order embedded in a UUIDv7 are observable implementation properties, never tenant authority, secrecy, or trusted domain chronology; security decisions continue to use authorized context and server-owned timestamp columns.

Retryable governed mutations enter `GovernedMutationExecutor`. Idempotency acquisition, first business execution, canonical audit insert, outbox insert, and cached-response completion share the authorized transaction and therefore commit or roll back together. PostgreSQL checks migration-owned event/version definitions, context metadata, payload keys and state transitions. Audit is append-only; outbox delivery is at least once using leases and unique claim tokens. At the receiving side, `ConsumerInboxExecutor` composes tenant authorization, unique receipt acquisition, and the first consumer effect in one transaction. V9's runtime-read-only consumer mapping is empty by default; forced-RLS receipts retain canonical-payload digests rather than payload copies, exact redelivery is skipped, changed content conflicts, and failed effects roll back their receipt. No publisher or consumer is started until non-interactive identity, tenant dispatch, production registry content, authenticated transports, and operational procedures are approved and implemented. See `GOVERNANCE_EVIDENCE.md`.

Browser authentication uses persisted password credentials, Redis-backed indexed sessions, Origin/Referer and CSRF checks, encrypted TOTP/recovery factors, recent-authentication evidence, throttling, and security-version revocation. The backend publishes the effective time to the earlier idle or absolute session deadline on valid authenticated responses. The checked client turns that signal and every `401` into session-lifecycle events; the React session feature locks locally at the deadline and performs full revalidation on focus, visible-tab, online, or BFCache return without using a background heartbeat that would extend idle life. The feature bootstraps and runtime-validates the session, locks protected content for anonymous/pending/mandatory-enrollment/error/no-membership states, and calls the checked client for primary login, generic password recovery, pending MFA, required or recent-authenticated TOTP enrollment/recovery-code handling, organization selection/switching, and acknowledged logout without browser-persistent credential state. The checked session response obtains authoritative MFA-enabled and role-required state from the persisted account; protected requests re-evaluate the live requirement so neither a pre-enrollment principal nor a role promotion can leave the UI authorized on stale state. Mandatory enrollment authority cannot load organizations, and the browser retains the workspace lock through one-time recovery-code acknowledgement. Password-reset tokens are captured case-safely from the email fragment, removed from the current browser-history entry, and retained only in memory until use. Organization selection is derived from live membership and stored server-side for navigation, but it is not authorization evidence. Every governed tenant operation must independently enter `TenantAuthorizationOperations`. The runtime-read-only catalogs now contain the checksum-approved `m1-candidate-1` interactive registry plus retained reference-only entries; unknown, retired, cross-version, ungranted, or non-enabled reference entries grant no permissions. High-risk approved operations can additionally require a separately recorded recent MFA timestamp. See `FRONTEND_SESSION.md`.

The `platform` module defines nine external-capability ports for document security, durable notifications, Redis jobs, workers, and schedulers. `PlatformCapabilityRegistry` requires exactly one readiness probe for every port family. The foundation supplies explicit unavailable adapters that throw before I/O and reports only safe state/reason codes at `/actuator/info`; Compose services are topology, not evidence that an application capability is active. An opt-in S3-compatible adapter implements private quarantine with tenant-derived keys, conditional writes, exact byte/digest verification, verified retry, and private-bucket startup checks. A separate opt-in ClamD adapter consumes only a scanner-internal quarantine stream, validates engine/protocol/signature freshness, bounds network streaming, and re-verifies content before returning a verdict. `DocumentSecurityOperations` checks the authorized transaction before either adapter is invoked and writes exact quarantine metadata plus every scanner observation through a mandatory PostgreSQL evidence adapter. The two append-only V8 tables use forced RLS, request-context triggers, server timestamps, restricted grants, and a composite tenant/object foreign key. Phase 0T adds `DocumentPromotionOperations`, a distinct opt-in private clean-bucket adapter, and V10 append-only promotion evidence: the application and database both require the authoritative latest `CLEAN` attestation to match the configured scanner/freshness policy, storage copies before evidence is recorded, and exact retries rehash the clean object. Phase 0U adds `DocumentAccessOperations`, an opt-in S3 GET-only signer, and V11 URL-free append-only access-grant evidence: committed promotion and an explicit purpose/TTL policy are required, the clean object is fully rehashed before signing, and matching evidence must be recorded before the authorized transaction returns the bearer URL. Phase 0V adds `DocumentRetentionOperations`, an opt-in S3 Object Lock adapter, and V12 append-only retention evidence: committed promotion, an explicit purpose/duration policy, exact current provider version, and full clean-object rehash are required before applying only monotonic `COMPLIANCE` retention or enabling a legal hold; exact predecessor lineage and only a hash of the provider version are persisted. The API cannot access low-level storage, scanner, promotion, signer, retention, or evidence ports. An opt-in Redis adapter uses tenant hash-slot keys and atomic Lua transitions for deduplicated enqueue, leased claim/ack, bounded retry, expired-lease recovery, retained dead letters, incremental cleanup, and safe telemetry. An opt-in PostgreSQL adapter persists notification parameters as AES-256-GCM ciphertext under forced RLS and provides hashed leases, bounded retry/dead-letter transitions, retained evidence, key rotation, and safe telemetry only inside an authorized tenant transaction. Module 7 now exposes governed upload, scan and purpose-bound access routes through the orchestration layer while keeping every provider disabled by default; it still does not implement hold release or disposal, authenticate a worker, authorize a queued effect, resolve recipient consent/destinations, or send a notification. See `PLATFORM_CAPABILITIES.md`.

The application delivery boundary is also fail-closed. Dockerfile bases, Compose dependencies, scanner overlays, and PostgreSQL/Redis test images are digest-pinned. The official PostgreSQL 18 service mounts its named volume at `/var/lib/postgresql` so the image can own its major-version-specific child directory; the dependency-free security contract rejects the legacy `/var/lib/postgresql/data` target. The final backend is a Java 25 Debian 13 distroless image running as UID 65532; the frontend is unprivileged Nginx on port 8080. Compose adds read-only root filesystems, writable `/tmp` tmpfs mounts, all-capability drops, and no-new-privileges for both application services. Spring and Nginx declare explicit response policies; the frontend's same-origin `/api` proxy permits a strict CSP and has bounded dependency timeouts. Synthetic successful dependency/browser/bootstrap fallbacks exist only in `application-local.yml`; the base and production paths require explicit identity/dependency values, and the production guard rejects documented local material plus insecure cookie, origin, database, Redis, SMTP, S3, and enabled-telemetry configurations. Full-SHA CI dependencies, least-privilege workflow settings, dependency review, CodeQL, Trivy source/image gates, CycloneDX SBOM generation, and a dependency-free repository contract protect this boundary. The Nginx listener remains HTTP, so TLS ingress, trusted proxy/service transport, secret-manager, rate/WAF, hosted-workflow, and production-registry enforcement remain deployment acceptance responsibilities. See `PRODUCTION_SECURITY.md`.

The forward-only migration chain now reaches `V113`. V14-V27 establish the approved identity and Module 1 authorization/configuration boundary; later migrations deliver the governed Module 2 workforce, Module 3 patient, Module 4 scheduling, Module 5 encounter, Module 6 assessment, Module 7 document/result, Module 8 AI-governance, Module 9 care-plan, Module 10 follow-up/outcome, Module 11 billing/payment, Module 12 reporting and Module 13 integration/FHIR models. V93-V95 bind the twelve-relation document/result boundary. V96-V98 release AI permissions/events and add 17 forced-RLS AI relations. V99-V101 release care-plan permissions/events, add ten forced-RLS care-plan relations and bind exact plan/version/assignment provenance to clinical tasks. V102-V104 release follow-up permissions/events, add seven forced-RLS follow-up/outcome relations, bind exact measurement/rule/escalation provenance to clinical tasks and preserve immutable definitions, measurements, escalation transitions, interpretations and digest-confirmed lifecycle evidence. V105-V107 release billing permissions/events and add fifteen forced-RLS financial relations with immutable monetary evidence and derived balances. V108-V110 release reporting permissions/events and add four forced-RLS relations with fixed aggregate metric catalogues, immutable run snapshots, governed schedules and exact-run expiring export requests. V111-V113 release integration permissions/events and add eight forced-RLS relations with secret-free registries, immutable mapping versions, replay-safe inbound evidence, exact outbox delivery/attempt lineage, separately authorized successor replay and profile-pinned FHIR provenance. The chain remains a repository implementation rather than production tenant provisioning or deployment acceptance. See `AUTHORIZATION_REGISTRY.md`, `GOVERNANCE_EVIDENCE.md`, the module implementation/completion reports, and `PLATFORM_CAPABILITIES.md` for detailed boundaries.

## HTTP contract

All MVC responses receive a validated or server-generated `X-Correlation-Id`. Application, validation, and security-filter failures use `application/problem+json` with stable CareOS error codes and correlation metadata. Both public operations, all 11 browser identity operations, both membership-backed organization-selection operations, three approved-registry invitation operations, three maker-checker MFA-administration operations, three bounded profile/readiness operations, six governed identifier operations, eight governed address/contact operations, one authorized membership-read operation, three governed membership-change operations, and three governed owner-transfer operations are checked into `contracts/openapi/careos-foundation.json`.

The contract also defines the required `/api/v1/organizations/{organizationId}/...` protected-business prefix, opaque cursor and bounded-limit components, operation-specific filter allowlists, strong `ETag`/`If-Match` concurrency, scoped idempotency, bounded multipart upload, caller-controlled retry semantics, and the no-polling session-deadline signal. A dependency-pinned generator produces checked TypeScript artifacts, and the browser client wraps all 135 current operations with credentials, CSRF bootstrap, correlation, strict response handling, session-lifecycle publication, and no automatic mutation retry. CORS permits `If-Match`/`Idempotency-Key`, exposes `ETag`/`Retry-After`/session-expiry metadata, and deliberately does not advertise `X-Organization-Id`. See `API_CONVENTIONS.md`.

The conventions remain the integration boundary. Modules 1 through 13 now expose checked server projections and governed mutations across administration, workforce, patient registry, scheduling, encounters, assessments, documents/results, AI assistance, care planning, follow-up/outcomes, billing/payments, reporting and integrations/FHIR. OpenAPI 0.52.0 contains 135 operations; generated-client drift, runtime response validation and strong-revision behavior fail closed. All 195 registered screens remain catalogue-checked, while live capability is determined by authorization, dependency readiness and each module's lifecycle—not by catalogue presence alone. Missing local policy, provider, profile or protected-source dependencies remain explicit unavailable states. Module 8's processing port is unavailable by default, every provider result remains draft until explicit clinician review, and AI cannot directly mutate an owning clinical aggregate. Module 9 requires complete intervention ownership/tasks, current consent, a clear exact-version safety review and eligible recent-MFA clinician approval before activation; amendments create successors instead of rewriting clinical evidence. Module 10 binds monitoring to the exact active plan, evaluates thresholds atomically, creates owned escalation tasks and preserves separate acknowledgement, resolution and interpretation evidence. Module 11 freezes price, estimate and invoice snapshots; derives balances from append-only monetary evidence; excludes card/provider secrets; and never allows financial state to rewrite clinical completion. Module 12 derives only fixed aggregate metrics, freezes exact bounded run snapshots, and keeps schedule execution and private export artifact delivery unavailable until accepted workers and storage exist. Module 13 retains only secret-free metadata and bounded evidence, requires exact outbox/profile/replay lineage and never treats transport success or FHIR validity as authority to change a source aggregate.

Module delivery has a separate fail-closed evidence boundary. The checked Module 1 manifest enumerates eight canonical input bundles and records `APPROVED` at package digest `19aff5ce30516b7ee2101c093a8429d8a74394995ca90d486790bcc18a392946`. Its dependency-free verifier hashes only regular files below `approved-inputs/module-1/`, rejects duplicate/incomplete/drifted evidence, and validates approval record `M1-APPROVAL-20260916-01` against the ordered M1-01 through M1-23 scope plus distinct checksum-matched approval evidence. Quality CI checks manifest consistency and fourteen attack fixtures; explicit `--require-approved` mode remains mandatory so later artifact drift fails closed.

## Scaling path

Start with multiple stateless backend replicas behind a load balancer, managed PostgreSQL, Redis, private object storage and independent job workers. Add read replicas and projections for reporting. Extract a service only when team ownership, deployment isolation or measured load justifies the operational cost. AI/ML remains an external port; a Python service can be added later without moving the Java clinical source of truth.
