# Frontend session boundary

## Scope

The React application now keeps protected route content behind the existing server-side browser identity and organization-selection APIs. This is a Phase 0 navigation/session boundary, not permission to perform a tenant business operation.

The `features/session` state machine calls the checked `CareOsApiClient` for:

- `GET /api/v1/auth/session` during bootstrap;
- `POST /api/v1/auth/login` for primary credentials;
- `POST /api/v1/auth/password-reset-requests` and `POST /api/v1/auth/password-resets` for public recovery;
- `POST /api/v1/auth/invitation-acceptances` for one-time anonymous account creation or exact authenticated existing-account linkage;
- `POST /api/v1/auth/mfa/challenges` when the server reports `mfa_required`;
- `POST /api/v1/auth/recent-authentications` before protected identity changes;
- `POST /api/v1/auth/mfa/enrollments`, its verification operation, and recovery-code regeneration for recent-authenticated self-service or server-required enrollment;
- the three organization-scoped administrative-MFA request, independent-approval, and execution operations;
- `GET /api/v1/organizations` after full authentication;
- `POST /api/v1/auth/organization-selections` for explicit selection or switching;
- governed organization invitation issue and revocation operations; and
- `POST /api/v1/auth/logout` for acknowledged session invalidation.

Every POST still goes through the client's per-mutation CSRF bootstrap, correlation validation, checked response handling, and no-automatic-retry rule.

The bounded `features/administration` state calls `GET /api/v1/organizations/{organizationId}/memberships` for M1-20. It sends only validated server filters and the preceding opaque cursor, runtime-validates the complete page/row/action projection, keeps cursor history in memory, and routes only server-advertised invitation or MFA-reset actions to the existing governed screens. At the approved shell breakpoint, the same projection renders as a keyboard-focusable table at 768px and wider or semantic record cards at 390/320px; both layouts reuse the same action component and never derive authority from viewport state.

The shared identity frame and authenticated workspace shell expose the approved keyboard-visible `Skip to main content` link. Because routing also uses the URL fragment, activation prevents fragment navigation and focuses the existing `<main>` directly. Identity-state and workspace-route changes focus the rendered `h1`, unless a descendant such as a problem summary already owns focus; this preserves actionable error focus while making successful navigation deterministic.

Local identity validation uses the same focus priority. Password-reset and invitation-acceptance failures focus a durable summary, mark the exact invalid input with `aria-invalid`, associate its message through `aria-describedby`, and expose a keyboard field link that focuses the control without changing the scrubbed hash route. Malformed one-use links and local invitation/MFA preparation failures also use the focused summary. Server-originated problems remain in `SessionIssueAlert` with their bounded retry and correlation details.

M1-02 offers the approved non-owner invitation roles, defaults to `organization_viewer`, retains a caller-owned idempotency key for an uncertain retry, and can revoke the returned pending invitation. The server—not the selector—enforces the caller's exact delegation ceiling, recent primary authentication, a separately recorded recent MFA assertion, reason, expiry, one-time token use, account-linking rules, and audit/outbox evidence. The browser never receives an issued raw token; delivery goes through the configured notification channel. Production activation remains off by default and is accepted only for the exact approved registry/package digest.

## Security invariants

- Credentials, MFA/recovery codes, invitation/reset tokens, session IDs, CSRF values, and organization selections are never written to `localStorage`, `sessionStorage`, or IndexedDB. Email-delivered one-time tokens necessarily arrive in the hash URL; the application captures them without case conversion, immediately removes them from the current history entry, holds them only in React memory, and forgets them after successful use. The server-issued `otpauth:` provisioning link is likewise transient and never placed in CareOS navigation or storage.
- Password, recent-authentication, MFA challenge, and enrollment-code React state is cleared when submitted. Plaintext setup material and recovery codes live only in a recently-authenticated child view and disappear when that view is closed, recent authentication is lost, or the route unmounts. The browser client does not log bodies and does not retry mutations.
- Generated TypeScript types are not treated as runtime proof. The session feature validates state/user/MFA-required/MFA-enabled coherence, UUID identities, organization shape and uniqueness, at-most-one selected organization, invitation/account-link results, administrative-MFA transition results, one-time enrollment material, and unique recovery-code format before rendering or revealing it. The administration feature separately validates every M1-20 page, cursor, membership field, and advertised action before rendering.
- The session response reads authoritative persisted MFA enabled/required status rather than trusting the potentially stale principal captured before an enrollment or role change. An authenticated-operation `401`, including `mfa-enrollment-required` after a mandatory-role promotion, returns the browser to the anonymous lock; `428` clears local recent-authentication status and requires credential verification again.
- The server emits the effective time remaining to the earlier Redis idle or absolute deadline on authenticated responses. The checked client derives a conservative local deadline from request start and publishes deadline updates and all `401` invalidations. The session feature uses a bounded timer, clears in-flight generations when the session ends, and keeps no deadline in browser persistence.
- There is deliberately no interval heartbeat. Idle pages therefore expire, including when background timer throttling delays JavaScript: visibility, focus, online, and BFCache-return handlers compare the deadline before making a checked revalidation request.
- Organization selection is only navigation state. Every future tenant operation must still carry its path organization into backend `TenantAuthorizationOperations`, where membership, purpose, and permission are revalidated transactionally.
- API, data, shared component, feature, and page dependency direction is enforced by `npm run architecture:check`. Features cannot directly import another feature, and shared layers cannot depend on a feature.
- Errors use the sanitized RFC 9457 client result. Raw exceptions, response bodies, credentials, and tokens are not rendered.

The frontend suite has 57 unit tests covering the checked transport/session boundary, mandatory-role enrollment and recovery-code acknowledgement lock, invitation issuance/revocation/acceptance, token scrubbing, account linkage, recent authentication, MFA enrollment/recovery codes, all three administrative-MFA transitions, identity/workspace heading focus, hash-safe skip/field navigation, focused field-associated local validation, exact readiness/profile states, permission-projected profile editability, M1-20 query encoding, runtime membership-page validation and compact record-card projection, strict registry lookup, unknown-route session precedence, honest synthetic action states, and non-activatable terminal pagination. Ninety-five Playwright tests exercise those browser flows plus mandatory enrollment at all five widths, login/selection/logout, password recovery, no-polling deadline locking, exact governed profile update, unknown-route focus/recovery, the generic interaction boundary, the approved-input source mockup, and M1-20 membership filtering/paging/action navigation at exact 1440, 1024, 768, 390, and 320 pixel widths. The identity/access cases prove reset/invitation validation focus and association, hash preservation, route-heading focus, and skip navigation in both frames at every width. M1-07 covers the approved field transport and responsive form; M1-20 explicitly requires record cards with no table at 390/320 and a table with no card list at 768/1024/1440. All 79 registered route states are Axe-checked and rejected for page-level horizontal overflow in every project; navigation checks distinguish the persistent shell from the 390/320 drawer, and result regions remain named and keyboard-focusable.

## Still required

This boundary now implements the approved invitation/account-link, governed administrator-reset, and mandatory-role MFA enrollment/use workflows. The database permits enabled-factor removal only through the exact governed reset, so active mandatory roles cannot self-disable; no self-disable endpoint is exposed. Optional viewer/editor organization enforcement or self-disable behavior remains unavailable unless separately specified and approved. The separate administration feature implements M1-05/M1-06 exact readiness, M1-07 exact approved profile/editability states, and M1-20 membership read plus governed organization-wide non-owner change/revocation and final-owner-safe owner promotion/demotion with server filtering, signed cursors, strong revisions, live permission-projected actions, and the approved responsive alternative without importing the session feature. Unknown hashes fail closed, and each remaining generic page clearly identifies synthetic data, keeps generic form/clinical fields read-only, forbids real-data entry, and leaves unimplemented workflow actions disabled instead of simulating success. M1B still needs approved facility-scoped membership grants, invitation inspection/resend/delivery behavior under separately authorized contracts, and explicit owner/target-environment acceptance. General business-record caching and the remaining Module 1 production slices also remain incomplete.
