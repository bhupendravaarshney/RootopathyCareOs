# Security and data-handling rules

- Never commit `.env`, database dumps, access tokens, private keys or real clinical data.
- Use synthetic seed data only in local development and automated tests. Keep the V19 Flyway placeholder hard-disabled in base/production configuration, and never bypass its changed/referenced-tenant remediation failure with a cascade.
- Keep every third-party CI Action pinned to a reviewed full commit SHA, retain its release comment, use read-only default permissions, discard checkout credentials, and bound jobs with explicit runners, timeouts, and concurrency cancellation.
- Do not merge dependency changes that fail dependency review, CodeQL, Trivy source/image scanning, repository security contracts, or existing quality gates. Treat a generated SBOM as inventory evidence, not proof that an artifact is safe.
- Keep Dockerfile bases, Compose services, scanner overlays, and Testcontainers dependencies digest-pinned. Refresh pins through reviewed update automation; never suppress a fixed HIGH/CRITICAL finding merely to make the gate green.
- Run the application images as their declared non-root users. Retain the Compose read-only root filesystems, `/tmp` tmpfs mounts, dropped capabilities, and no-new-privileges settings unless a reviewed threat model and test prove a narrower change is required.
- Automated database tests must use the disposable PostgreSQL 18 `careos_test` container; they must never point at `careos_dev` or production.
- Mount the official PostgreSQL 18 Compose data volume at `/var/lib/postgresql`, never the rejected legacy `/var/lib/postgresql/data` target. Existing retained clusters require a supported backup/upgrade procedure; do not treat a mount change or volume reset as a database upgrade.
- Keep the approved Module 1 input manifest, all eight artifacts, approval evidence, and their recorded SHA-256 values unchanged unless a new accountable approval replaces the package. Production Module 1 work requires `verify-module-1-inputs.mjs --require-approved`; never weaken the gate, silently substitute an artifact, or treat a later design/policy edit as covered by `M1-APPROVAL-20260916-01`.
- Only authenticated membership/policy code may construct an `AuthorizedTenantContext`; never trust an organization header directly.
- Every tenant-owned transaction must set and verify transaction-local organization, actor, purpose, and correlation context.
- Run Flyway with the migration owner and all application queries with the restricted non-`BYPASSRLS` role.
- Generate new application identifiers only through the shared `UuidV7Generator` and retain native PostgreSQL 18 `uuidv7()` defaults for database-generated identifiers. Do not reintroduce direct production UUIDv4 generation, rewrite or reject valid historical/reference UUIDs, or treat a UUIDv7 timestamp/order as authorization, secrecy, or trusted event chronology.
- Enforce authorization in application policy and forced RLS.
- Treat the stored organization selection only as a navigation preference; revalidate membership and permission inside every governed tenant transaction.
- Keep authorization registry tables migration-owned and runtime-read-only; an unknown or retired role, permission, or mapping must grant nothing.
- Keep audit/outbox event-version registries migration-owned and runtime-read-only; reject unknown/retired events and payload-key drift.
- Use private object storage, quarantine and fail-closed malware scanning for credential and clinical documents.
- Keep document quarantine, scanning, clean promotion, signed access, retention, durable notifications, Redis jobs, workers, and schedulers explicitly unavailable by default until a tested adapter is intentionally configured for each capability; infrastructure presence alone is not capability readiness. Promotion, signed-read, and immutable-retention/legal-hold-enablement mechanics are implemented but remain separately opt-in and do not constitute an approved document-delivery or disposal workflow.
- Treat quarantine as untrusted: storage success never authorizes download or promotion, and every downstream operation remains denied until matching, durable `CLEAN` evidence satisfies an approved freshness rule and its own approved adapter exists.
- A scanner may read quarantine only through the internal tenant-checking content boundary. Never expose that stream through an API, trust a daemon verdict without local size/digest verification, or convert timeout, stale definitions, protocol drift, oversize input, or dependency failure into `CLEAN`.
- Route quarantine and scanning through `DocumentSecurityOperations`, promotion through `DocumentPromotionOperations`, signing through `DocumentAccessOperations`, and retention through `DocumentRetentionOperations`; API packages must not invoke storage, scanner, signer, promotion, retention, or low-level evidence ports. Require an active writable `AuthorizedTenantContext` transaction before external I/O, accept only the expected opaque tenant/document/object-version reference, and persist the result before treating it as evidence.
- Keep V8 quarantine metadata and scan attestations append-only under forced RLS, restricted `SELECT`/`INSERT` grants, transaction-context triggers, database timestamps, and the composite tenant/object foreign key. Exact retries may converge, but changed quarantine metadata or contradictory scanner observations must fail. `CLEAN` and `INFECTED` require the authoritative digest; retain `ERROR` observations even when the digest is unknown, and never use them for promotion.
- Keep V10 clean-promotion evidence append-only under forced RLS and restricted `SELECT`/`INSERT` grants. A promotion must reference the deterministic latest scan, whose verdict is `CLEAN`, scanner is on the snapshotted allow-list, digest matches the quarantine object, and observation time satisfies the snapshotted age/future-skew policy at both application and database boundaries. Copy to a distinct private clean bucket before recording evidence, retain quarantine, and treat an orphaned private clean copy after a database failure as non-authoritative until an exact retry records evidence.
- Keep V11 signed-access grant evidence append-only under forced RLS and restricted `SELECT`/`INSERT` grants. Require committed V10 promotion evidence, an approved current tenant purpose, a recent bounded authorization, exact TTL/expiry, and a fully rehashed ETag-bound clean object before signing only `GET`. Never persist or log a bearer URL, query signature, credential, bucket, or object key; a signer or evidence failure must prevent the coordinator from returning the URL.
- Keep V12 retention evidence append-only under forced RLS and restricted `SELECT`/`INSERT` grants. Require committed V10 promotion, an approved purpose/duration policy, recent authorization, exact latest-predecessor lineage, and a version- and ETag-bound full clean-object rehash. Apply only S3 Object Lock `COMPLIANCE` to the exact provider version and permit only deadline extension or legal-hold enablement. Never bypass governance, shorten retention, disable a hold, delete content, or persist/log a bucket, object key, or raw provider version; retain only its SHA-256 identifier in evidence.
- ClamD TCP is unauthenticated and unencrypted. Keep it on a trusted private network, never publish port 3310 from the local overlay, and require production network policy, signature-update monitoring, resource limits, and operational ownership.
- Redis queue keys must be derived from an authorized tenant, share a tenant hash slot, contain no raw deduplication token, and transition only through bounded atomic scripts. Never log job references or lease tokens, accept an unapproved job schema, acknowledge a stale/cross-tenant lease, or treat queue presence as authorization to execute work.
- Keep Redis job transport separate from worker activation. Production requires authenticated non-interactive identities, tenant reauthorization, ACL/TLS/HA/persistence and restore acceptance, metrics/alerts, dead-letter review/replay, and governed evidence before a worker may claim jobs.
- Store durable notification parameters only as authenticated ciphertext under a named 256-bit key; store only hashes of deduplication and lease tokens. Never persist or log a recipient destination in the queue, return parameters through an API, deliver under a stale/cross-tenant lease, or discard retained terminal evidence early.
- Keep notification persistence separate from delivery activation. At delivery time, an authorized non-interactive worker must re-resolve current consent and destination, use an approved provider/idempotency contract, and record approved governance evidence. The Phase 0J adapter performs none of those delivery actions.
- Require HTTPS, distinct dedicated private quarantine and clean buckets, provider-level public-access controls, least-privilege IAM, KMS-backed encryption, governed metadata, enabled versioning, and pre-provisioned Object Lock before accepting document storage, promotion, signed access, or retention for production; the pinned local compatibility server is not production approval.
- Log metadata and governance evidence, never passwords, MFA seeds, recovery codes, raw invitation tokens or unnecessary clinical text.
- High-risk operations require MFA, recent authentication, mandatory reason and maker-checker separation where defined.
- Treat `careos-phase0-reference-v1` and `local_bootstrap` as reference-only. Production must continue rejecting the reference-policy flag and service-identity activation. Governed invitations and administrative MFA reset may be enabled only when the active registry is `m1-candidate-1`, its configured approval-package digest is `19aff5ce30516b7ee2101c093a8429d8a74394995ca90d486790bcc18a392946`, and V20 release evidence is present; all other registry/digest combinations fail closed.
- Administrative MFA reset must retain V17's exact lifecycle: a non-target maker requests for another active MFA-enabled member, a different non-target authorized checker decides, and only the original maker consumes the unexpired approval using the exact target, original reason, and execution idempotency key. Expired rows may become `expired` to permit a replacement but must never be deleted or repurposed.
- Service credentials must be generated and delivered outside browser flows, stored only as bounded expiring HMAC digests, and authorized through `ServiceIdentityAuthorizationOperations` for an exact tenant, purpose, non-interactive role, and operation. Never assign a service role to a human membership or use a human session as a worker identity.
- General audit records are database-enforced append-only evidence. Outbox event content is immutable and non-deletable; only validated lease, acknowledgement, retry, and dead-letter metadata transitions are allowed.
- Retryable governed mutations must use `GovernedMutationExecutor`; never commit business data separately from its audit, outbox, and idempotency evidence.
- At-least-once CareOS consumers must use `ConsumerInboxExecutor`; never commit a consumer effect separately from its unique tenant/consumer/source-event receipt, and never acknowledge a broker message before the transaction commits.
- Keep consumer definitions migration-owned and runtime-read-only. Accept only active consumer/event-version mappings and approved top-level payload keys; retain a SHA-256 digest of PostgreSQL-canonical JSON rather than duplicating payload content in inbox evidence.
- Keep V9 consumer receipts under forced RLS with `SELECT`/`INSERT`-only runtime grants and append-only owner enforcement. Exact canonical redelivery may skip its effect, but changed envelope content under the same source ID must fail; transport authentication, service identity, governed replay, monitoring, and retention remain separate requirements.
- Scope request replay records by organization, authenticated actor, operation, and key; never log keys, request bodies, response bodies, or transport exception text.
- Browser authentication uses persisted credentials and Redis-backed server-side sessions; HTTP Basic and default form login must remain disabled.
- Production session cookies must set `Secure`; local HTTP development is the only permitted exception.
- Run the production profile without `local` or `test`. It must reject documented non-production secret material, non-canonical/HTTP browser origins, plaintext PostgreSQL or Redis, optional SMTP downgrade, unsafe S3 local overrides, incomplete promotion/signed-access/retention policy activation, and a plaintext enabled OTLP exporter; inject real values only through an approved audited secret manager.
- Preserve the explicit Spring API and Nginx response-header contracts. The frontend CSP must remain same-origin without wildcards, `unsafe-inline`, or `unsafe-eval`; do not weaken it to integrate a vendor without a reviewed purpose, data-flow, and narrow directive.
- The repository Nginx listener is not a TLS endpoint. Production must terminate approved TLS, redirect plaintext traffic, keep backend/management access private, define trusted forwarding and service-hop transport, and test certificates, headers, renewal, and failure behavior on the real hostnames.
- Login/MFA throttling is not a general abuse boundary. Approve and test application/edge rate limits, body/connection limits, WAF/DDoS rules, false-positive handling, emergency change audit, and accessibility-safe failures without treating IP reputation as tenant authorization.
- Keep protected business routes under `/api/v1/organizations/{organizationId}/...`; never accept an organization header as tenant authority. Browser CORS must allow checked concurrency/idempotency headers and expose correlation/retry/ETag/session-expiry response metadata without reintroducing `X-Organization-Id`.
- Generate frontend API types only from the checked local OpenAPI document and fail CI on drift. Do not hand-edit generated files, weaken strict indexed access, or remove a dependency-security override without a clean replacement audit.
- Browser API calls must include credentials and a validated correlation ID. Obtain and validate the exact CSRF header/token contract before each unsafe request; do not send the mutation when bootstrap fails and never set `Origin` from JavaScript.
- Do not automatically retry browser mutations. Caller-retried governed mutations require a scoped idempotency key; mutable updates/deletes require a strong `If-Match`; cursors are opaque and filters are operation allowlists. Treat malformed statuses, media types, correlation headers, Problems, ETags, cursors, and retry delays as contract failures.
- Keep protected frontend content behind runtime-validated server session and membership-backed organization responses. Store no password, MFA/recovery code, session ID, CSRF value, or selected organization in browser persistence; clear submitted secret field state and fail closed on malformed, ambiguous, or unavailable responses.
- Require the bounded server session-expiry signal before exposing authenticated content. Update its memory-only deadline from checked authenticated traffic, lock locally when it passes, and revalidate on browser return only while it remains unexpired. Never add an interval heartbeat that defeats Redis idle expiry.
- Treat password-reset and MFA enrollment material as transient secrets. Preserve reset-token case, replace the token-bearing browser-history entry immediately after capture, retain it only in memory until successful use, and runtime-validate `otpauth:`/recovery-code output before display. A `401` must relock the browser and a `428` must require recent authentication again.
- Treat frontend organization selection only as navigation context. A switch must be server-acknowledged, a failed logout must not be presented as success, and each future business call must still enter transaction-bound backend authorization. Keep the frontend feature dependency gate in CI.
- Invitation/account-link and maker-checker MFA-reset mechanics now bind to the approved Module 1 authorization/event registry, require the approved recent-MFA assurance, and remain disabled by default unless the production digest guard above passes. Non-interactive reference authorization, consumer/template/retention activation, service credential provisioning/rotation and actual workers, legal-hold release/disposal, production platform acceptance, consent/destination transports, and real producer/consumer wiring remain fail-closed until their governed implementations exist.

Report security problems privately to the designated CareOS security owner. Do not include patient information in issue trackers.
